# Фактична поведінка API там, де вона розходиться з документацією

Відбір за критерієм «чи наштовхнеться на це агент-аналітик». Кожен пункт —
з датою заміру і формою виклику. Тон — опис поведінки, не претензія: API
не «зламаний», він просто поводиться інакше, ніж очікує документація чи
здоровий глузд, і саме тому це варто знати заздалегідь, а не виявити на
чужих даних.

Пункти 1–7 перевірені живими прогонами 17–18.08.2026 на `auspex.uspacy.ua`.
Пункт 8 доданий 05.09.2026 і описує межу набору інструментів, а не самого
REST API.

1. **Статуси задачі.** `POST /tasks/v1/tasks` записує лише `scheduled` і
   `ready`. `inWork`, `notScheduled`, `stopped` приймаються з `201` і
   мовчки стають `scheduled`. `PATCH /tasks/v1/tasks/{id}` ті самі
   значення пише чесно. Наслідок для роботи через MCP: `tasks_create` не
   можна довіряти статус одразу — потрібен другий виклик, `tasks_update`,
   якщо статус відрізняється від дефолтного.

2. **Статуси справи (activity).** Валідні рівно `done` і `planned`.
   `scheduled`, `new`, `open` дають чесний `422` — тут API не мовчить, на
   відміну від задач. Прострочена справа — це `planned`, чий `start_time`
   уже в минулому, а не окремий статус на кшталт `overdue`; рахувати
   прострочені справи — значить порівнювати `start_time` з поточним часом
   (правило 6: час бере з `GET /company/v1/users/me/settings`, поле
   `timezone`), а не шукати спеціальне значення статусу.

3. **Кошик.** Видалення в REST API — перенесення, а не знищення:
   `GET /crm/v1/entities/{entity}/trash` показує вміст,
   `PATCH .../trash/restore` повертає запис. Це механізм самого API;
   агент через MCP жодного з цих двох шляхів викликати не може — див.
   `mcp-coverage.md`, розділ «Не покриває». Знання про механізм лишається
   потрібним: пояснити людині, що сталося з видаленим записом, можна й
   без прямого доступу до кошика.

4. **`mass_deletion`.** `DELETE /crm/v1/entities/{table}/mass_deletion` з
   тілом `{"all": false, "entity_ids": [...], "except_ids": []}` ігнорує і
   прапорець, і список id — виноситься вся колекція. Заміряно на
   реальних даних: 721 лід, 746 компаній, 12 угод пішли в кошик замість
   трьох переданих id. Це не гіпотетичний ризик — це причина, з якої
   плагін не викликає жодної операції видалення (правило 1 в `SKILL.md`).

5. **Кириличні коди довідників.** `POST` на `/crm/v1/lists/{code}` (сам
   довідник у MCP не покритий — див. `mcp-coverage.md`, але поведінка
   важлива, якщо ці дані видно через інші канали) повертає `200` і
   транслітерує коди: `діагностика` → `d_agnostika` (цей самий патерн
   транслітерації видно в кодах етапів воронки «Сервіс і монтаж» —
   `d_agnostika`, `vi_zd_priznaceno`, `pogodzennia_vartost_`, отриманих
   через `crm_list_funnels`). Запис із кириличним значенням, який очікує
   збереження саме кириличного коду, лишається з ПОРОЖНІМ полем.

6. **`GET /crm/v1/static/product-categories`** відповідає без `meta.total`
   — рахувати категорії за цим полем не можна, лічильник за такою
   відповіддю завжди дасть нуль. Той самий простір імен, що й товари
   (`mcp-coverage.md`), і той самий наслідок: тиша замість чесної нуль-
   відповіді, якщо не знати про цю особливість заздалегідь.

7. **Частота запитів не обмежена** (замір: 1 потік ≈ 1/сек, 8 ≈ 8/сек,
   24 ≈ 15/сек, жодного `429` на 152 викликах). Це довід за акуратність
   роботи з чужим порталом, а не привід молотити його: відсутність ліміту
   з боку сервера не знімає відповідальності з клієнта.

8. **Повний перелік типів сутностей на цьому порталі.**
   `crm_list_entities` (`GET /crm/v1/entity`) повертає рівно шість:
   `leads`, `deals`, `contacts`, `companies`, `uspacy_transactions`
   («Transactions», з підтримкою задач і справ) і `servsn_zaiavkis`
   («Сервісні заявки», тип `universal` — розумний об'єкт клієнта, теж з
   підтримкою задач і справ). Це не властивість API взагалі, а стан
   конкретного порталу — на іншому порталі перелік типів буде іншим, і
   перед аналітичним запитом його варто звірити заново, а не покладатись
   на цей список як на канонічний.
